wglan field guide

A reference for colleagues evaluating the design: what it does, where it fits, and exactly how a node joins, restarts, departs, and reaches a peer's service. The normative version is SPEC.md; this document is the argument, not the contract. References to wgmesh throughout are to the larger mesh daemon this design was cut down from — cited as prior art, and as evidence for the choices that go against it.

01 · Features

What it does

Every feature below exists because a real requirement demanded it — nothing is speculative.

Shared-secret join

One secret to join the mesh. No accounts, no control-plane login, no server to trust. The secret derives the envelope key — sealing a message is the proof of membership, so there is no token to carry.

Operator-chosen subnet

You pick the mesh subnet once, checked against what your LAN already routes — not a random 10.x.y.0/16 a key derivation function picked blind.

Static addressing

--mesh-ip 10.90.0.3/24 per host, from the inventory you already keep. No assignment protocol means no address two nodes can disagree about.

Full mesh from one bootstrap IP

Point a new node at any one existing member. Every pair ends up directly peered — proven by induction, not gossip.

Zero ongoing background logic

The daemon is an idle listener. No reconcile loop, no beacon, no timers running in steady state.

WireGuard-native liveness

Endpoint drift and reachability ride on WireGuard's own roaming + PersistentKeepalive — no custom protocol.

Symmetric join and leave

One command joins and propagates mesh-wide; leave departs the same way. Liveness is detected and reported, never auto-evicted.

Survives a reboot

The peer list persists locally. A restart reloads it directly and never re-bootstraps.

Human-readable names

Writes <node>.mesh entries into /etc/hosts — real FQDNs, no DNS service to run.

Small enough to read in one sitting

Standalone Go binary, shells out to wg/ip, no library dependency beyond WireGuard itself.

By design, not by omission

  • No revocation — membership is "knows the secret," permanently. Excluding a node is a flag day, not a command: every node's envelope key comes from the secret, so old- and new-secret nodes can't exchange anything, and the mesh is partitioned until every kept node is rotated. wgmesh looks like it solves this — rotate-secret, a signed announcement, grace-period machinery — but the command builds the announcement and drops it (_ = announcement) and prints the same manual steps. Nebula is the real exception: identity in a signed cert with a lifetime, so revocation is "let it lapse." If the requirement ever appears, that's the answer — short-lived certs, not a revocation list.
  • No automatic eviction — a peer that stops answering is marked stale in status, never removed on its own and never reported to other nodes. See Departure & death for why broadcasting one node's opinion is the dangerous part.
  • No DHT, no internet-facing discovery — LAN and one bootstrap IP only. This is what makes the offline claim actually true.
  • No ACLs, mobile clients, GUI, or IPv6 — not requirements for this design; not built.
02 · Use cases

Where it fits

Scenarios this design was shaped around — not a generic feature checklist.

01

Home-lab service mesh

A handful of self-hosted boxes on one LAN, each running Docker services the others need to reach by name over an encrypted tunnel — without exposing anything on the LAN itself.

fits because: static addressing + /etc/hosts naming, zero reverse proxy needed
02

Air-gapped internal network

A lab or industrial network with no internet access at all. Needs encrypted node-to-node connectivity with nothing external to fail against.

fits because: no DHT, no rendezvous server, no bootstrap dependency outside the LAN
03

Slow, deliberate onboarding

Roughly one new machine a day, not a fleet churning constantly. A single join command with one bootstrap IP beats maintaining a registry or running a beacon.

fits because: no reconcile loop, no revocation machinery, low-churn by design
04

Reboot-resilient nodes

A node reboots for a kernel update or power blip. It should rejoin on its own from what it already knew, not wait on an operator to re-run a join command.

fits because: persisted peer list, restart skips bootstrapping entirely

04 · Wire format

One sealed message, and why there is no token

Every arrow in the sequences above is the same thing on the wire: a single AES-256-GCM envelope. Authentication and confidentiality are not two features here — they are one primitive, and that is what closes the threats below.

✓ decided

Sealing the message is the proof of membership

The envelope key is derived from the shared secret, so producing a message that opens at all proves the sender holds the secret. An earlier draft carried a separate HMAC proof-token and left the payload in cleartext; that was strictly worse on both counts — it disclosed the whole peer list to any passive listener, and because the token covered only the sender's pubkey, every other field stayed forgeable under a captured token. wgmesh itself settled this the same way: its runtime authenticates every wire path by "the envelope opened", and the membership-token primitive it also ships has zero non-test callers.

Outer frame — the only bytes a stranger can influence

[uint32 length]   hard cap 4096 — larger is dropped without reading the body
{
  "nonce":      base64,   // 12 random bytes, fresh per message
  "ciphertext": base64    // GCM tag covers the entire sealed payload
}

Sealed payload — every field below is encrypted and tamper-evident

FieldTypePurpose
protocolstring"wglan-v1" — fails closed on version skew before any other field is read.
typestringJOIN or JOIN_REPLY.
timestampint64Unix seconds. The freshness bound. Inside the seal, so it cannot be edited.
pubkeystringSender's WireGuard public key — 44 base64 chars, decodable to 32 bytes.
hostnamestringSender's mesh hostname, ^[a-z0-9-]{1,63}$. Goes into /etc/hosts, so it must never hold whitespace or path metacharacters.
mesh_ipstringSender's configured mesh address. No mask — the mask is local-only.
lan_endpointstringSender's ip:port for the WireGuard UDP data plane.
peers[]arrayJOIN_REPLY only — {pubkey, hostname, mesh_ip, lan_endpoint} per known member, capped at 256. This field is why confidentiality matters: one captured reply is the entire network map, not one node's details.

Freshness: a payload more than 10 minutes old — or more than 10 minutes in the future — is rejected. Both directions on purpose: rejecting only "too old" would leave a future-dated capture replayable indefinitely once its time arrived.

Validation is welded to the open: one function opens the envelope, checks the protocol, checks freshness, unmarshals, and validates every field. No code path yields an unvalidated struct. A rule that callers must remember is a rule that eventually gets forgotten.

What stops each threat

ThreatMitigationResidual
Stranger joins the mesh Cannot produce an openable envelope without the secret. none
Passive eavesdropper maps the mesh — pubkeys, hostnames, addresses, endpoints Whole payload sits inside the AEAD. Nothing readable on the wire. none
Tampering with a captured message — the serious one: rewriting mesh_ip repoints a peer's AllowedIPs and /etc/hosts entry, and with no reconcile loop nothing ever repairs it GCM tag covers the entire payload. Any edit fails the open. none, from a non-member
Verbatim replay inside the window Not prevented — and does not need to be. A JOIN says "peer X is at address Y", so applying it twice equals applying it once. No nonce cache, deliberately; wgmesh ships none either, for this reason. Only matters if JOIN ever gains a non-idempotent side effect. Add a seen-set then, not before.
Replay of a stale or future-dated capture Freshness check, ±10 min, inside the seal. Bounded to a 10-minute window.
Pre-auth resource exhaustion 4KB framed read, 3s deadline, 8-connection semaphore, and a per-source-IP rate limiter applied before the decrypt attempt — so a stranger cannot make the node burn AES cycles on garbage. A LAN-local flood can still deny joins while it runs. Joins are manual and rare; accepted.
Parser oracle A failed open is the only rejection reachable pre-auth, and it is uniform. Wrong key, wrong version, stale timestamp and malformed bytes are indistinguishable on the wire by construction — not by carefully ordering hand-written checks. none
Injection into wg/ip//etc/hosts Strict per-field validation as a precondition, plus exec.Command argv-array form exclusively — never a shell string. none
A member forges another member's address Not mitigated. Anyone holding the secret is inside every gate above by definition. Deterministic addressing would let a receiver verify mesh_ip == derive(pubkey); static addressing forecloses that permanently. Accepted — consistent with a design where membership is total and permanent (no revocation, no ACLs). The substitute is loud logging: an address or hostname change is logged differently from a first-sight add, naming old and new. That cannot prevent the forgery, but it makes silent persistent poisoning impossible to miss.
✓ free safety

sync is safer than JOIN, at no cost

JOIN has to run outside the tunnel — at bootstrap there is no tunnel yet. sync runs between members that are already peered, so it binds the mesh address and travels inside the tunnel: WireGuard's cryptokey routing has already authenticated the sender before a single line of wglan code runs, and the envelope is belt-and-braces on top. This is exactly how wgmesh's gossip layer works.

05 · Departure & death

Leaving is a message. Dying is not.

Three situations get bundled into one feature request. They get different answers because they carry different amounts of certainty — and the third one is where an obvious design does real damage.

SituationWho knowsMechanism
Planned decommission or rebuild The departing node, with certainty leave — one command, fans out to every peer, done
Cleaning up after a node that's already gone The operator forget <pubkey>, run per node
Silent loss of connectivity Nobody, reliably Detected locally, marked in status, corroborated with probe, acted on by a human

Leaving: fixing an asymmetry that was already there

Joining is one command that propagates mesh-wide. Removing a node was forget on all N−1 others. wglan leave seals a LEAVE and sends it to every peer in peers.json — reusing the exact fan-out the joiner already performs. The mechanism to make departure symmetric already existed.

Not sent from a shutdown hook. A node stopping for a reboot has not left the mesh. Announcing departure on every restart would turn the common case into the rare case's message. leave is an explicit operator action.

⚠ required constraint

A LEAVE is only honoured inside the tunnel, from that peer's own mesh address

A sealed message proves "the sender holds the secret" — not "the sender is the pubkey named inside." Without this constraint any member could evict any other member. wgmesh has exactly this hole: its GOODBYE handler removes whatever pubkey the message names, with no binding to the sender. It's survivable there because the reconcile loop re-adds the victim; here it would be permanent. Requiring the message to arrive over wglan0 from the departing peer's own mesh IP makes WireGuard's cryptokey routing prove the sender's identity before a line of wglan code runs.

LEAVE is a cooperative convenience, not a security control. A hostile or crashed node simply never sends one — which is exactly why the third row above needs a different answer.

Death: detected locally, never broadcast

Detection is free — WireGuard already tracks it and status already shells out for it. Two signals, not one, borrowed from wgmesh's shouldTreatPeerAsStale: a handshake older than the threshold and transfer counters that haven't grown. Handshake age alone misleads, because a peer with nothing to say looks idle while being perfectly healthy. 

$ wglan status
node4.mesh   10.90.0.4   192.168.1.24:51820   handshake 18s
node7.mesh   10.90.0.7   192.168.1.27:51820   stale (4d, no transfer)

$ wglan probe node7
node7: unreachable from 11/11 peers (stale 4d)   # confident — forget it everywhere
node7: unreachable from 1/11 peers (stale 4d)    # your link is broken, not node7

That's the whole liveness feature: it reports, a human decides. probe gathers the same evidence a distributed failure detector would — the quorum intact — but on demand, when someone is already looking, with no standing machinery and no automatic action.

✕ considered and rejected

Automatic eviction on missed handshakes

  • "Dead" and "unreachable from here" are indistinguishable to one observer — not a gap to close with more code, but the property that makes distributed failure detection hard, and the reason real systems use quorums or leases instead of one node's opinion.
  • The mistake would be permanent — see the diagram. No reconcile loop to undo it, and it's persisted, so it survives restarts.
  • The cost of not evicting is an inventory cost, not a runtime cost — rotted status output, a stale node7.mesh that fails slowly (connect timeout rather than NXDOMAIN), and a mesh address held against reuse by the duplicate-address check. All human-visible, none breaking. Inventory is operator-owned by design, so these want a human decision — exactly what automation removes.
  • wgmesh already decided this, with every mechanism available to decide otherwise — it has a reconcile loop, gossip, a health checker, and a peerStore.Remove(). Its detector fires and the action is attemptPeerReconnect: re-apply the config, force a fresh handshake. It never removes, never marks dead, never tells another node. peerStore.Remove has exactly one call site in the entire codebase — the GOODBYE handler. Removal happens only when a peer says it's leaving.

If it's ever genuinely wanted, the minimum safe shape is soft state only (mark unreachable, never remove — so a false positive costs a wrong label, not a broken mesh) plus majority agreement before even the mark propagates. That's a periodic detector, a gossip round, and a quorum rule: the reconcile loop this design deleted, plus a consensus mechanism it never had. A deliberate reversal, not an edge feature.

06 · Exposing services

One peer per service, not a subnet behind one

The mesh has no concept of "a network behind a peer" — every service that needs to be reachable joins as its own peer, the same way a physical node does.

ServiceRuns asWhy this shape
HTTPS container, own peer Single well-known port — but kept uniform with the others rather than mixed with a Docker -p bind, so there's one mental model for every exposed service.
SIP / media failover container, own peer
--cap-add NET_ADMIN --device /dev/net/tun		 RTP negotiates ports from a wide dynamic range per call — a real routable IP avoids enumerating them, and avoids NAT breaking SIP/RTP the way it classically does in telephony.
IdM replication KVM VM, own peer
(no extra capabilities needed)		 Needs a wide, fixed set of ports (LDAP, Kerberos, DNS, HTTP). A VM already has its own full network stack, so it joins exactly like a physical node — no capability grants at all.
✕ considered and rejected

Routing a subnet through one peer

The alternative was extending one node's WireGuard AllowedIPs to cover an entire Docker subnet (e.g. 172.20.0.0/24) behind it, so every container on that host became reachable at once. Rejected for one durable reason:

  • All-or-nothing exposure — a routed CIDR can't distinguish one container from another; anything added to that subnet later is implicitly reachable too, with no deliberate step exposing it. Even a fully engineered version of this feature — validated, persisted, logged — still routes the whole block at once, because that's what CIDR-based routing means, not a gap in how it's built.

What one-peer-per-service gains

  • Deliberate, individually auditable exposure — every reachable service is a specific JOIN, visible in status and the join log. Nothing rides along implicitly just because it happens to share a host with something else.
  • No gateway single point of failure — every peer holds direct WireGuard tunnels to everyone. There's no one node that, if it goes down, takes a whole set of otherwise-healthy services with it the way a subnet's routing gateway would.
  • No NAT or forwarding to configure or get wrong — each peer gets a real, direct mesh IP. No ip_forward, no FORWARD-chain rules on a gateway host, no risk of Docker's own iptables management fighting a manually-added route.
  • One addressing scheme, one firewall shape, everywhere — every peer takes its address from one inventory and gets the exact same wglan0 default-deny skeleton. Nothing to reconcile between "mesh addressing" and a foreign subnet's own addressing, and no special gateway-forwarding ruleset that needs different reasoning from every other node's.

What one-peer-per-service gives up

  • Anything that can't run wglan itself — a hardware appliance, a printer, an IoT device, a closed third-party box. One-peer-per- service assumes whatever you're exposing can install and run the daemon; subnet routing is the only way to reach something that fundamentally can't.
  • Transparent site-to-site bridging — merging two existing LANs (or reaching a pre-existing subnet by its own real addressing) isn't possible this way. Every peer gets an address out of the mesh subnet; nothing lets an entire foreign network keep its own addressing and just become reachable.
  • A dynamically scaling or highly ephemeral fleet — autoscaled containers, CI-spun instances — reachable without onboarding each one individually. Every peer here is a deliberate, one-time JOIN; that's a feature at your actual churn rate (~1/day) but a real limit if something needs to scale fast.
  • Administering reachability as one unit instead of N — one route covers a whole subnet with one line of config; one-peer-per-service means one keypair, one persisted identity, and one join event per thing exposed, which only stays cheap because the list here is small and constant.

Every service that needs mesh reachability becomes its own peer instead — same JOIN, same persistence, same status visibility as any physical node. None of the four gaps above apply to HTTPS, IdM, or SIP/media today — worth revisiting only if a future service can't run the daemon itself, or needs to scale faster than this design assumes.

07 · Host firewall

Split ownership: skeleton vs. rules

Joining the mesh exposes whatever a host already has listening on 0.0.0.0 — not just what it meant to expose. SSH "just works" over the mesh for exactly that reason; anything else bound broadly on that host is exposed the same way, with no deliberateness at all. That splits into two different concerns, owned by two different things.

The daemon owns

One idempotent check at startup: does the wglan / wg0_in table exist with policy drop? If not, create it — empty, no rules, no knowledge of ports or peers. If it already exists, touch nothing. This is a fail-closed starting state, not a policy engine — the same bar already applied to the JOIN listener itself.

Config management owns

The actual allow-list, inserted into that same daemon-created chain — never a separate table. Every node allows 22 for SSH; the HTTPS peer additionally allows 443; and so on. This is exactly the per-node variation Ansible host/group vars are for. 

table inet wglan {
  chain wg0_in {
    type filter hook input priority 0; policy drop;
    # iif "wglan0" tcp dport 22 accept   <- inserted per node, e.g. via Ansible host_vars
  }
}

Scoped by interface (iif "wglan0"), not by IP. With static addressing the mesh IP is known ahead of time, so this is no longer forced — it's still preferred, for two reasons: iif "wglan0" needs neither the address nor the interface to exist yet, so there's no ordering dependency between the skeleton, the allow-list, and wglan join actually running; and it stays correct across a renumber, which an address-scoped rule would not. No drift detection beyond the skeleton itself — the daemon never checks what's listening outside the allow-list, the same way it doesn't do ACLs or revocation. Only the guarantee that nothing gets through until something explicitly says otherwise is built in.

08 · Packaging

Bootc & Quadlets: readiness ordering

On a bootc host, the rpm is baked into the image and a Podman Quadlet exposes the service. The address itself is known from the inventory before the machine ever boots — what isn't ready at boot is wglan0: the interface has to exist and hold that address before anything can bind to it. That ordering, not address discovery, is what readiness gating buys. This is a recommended packaging pattern, not yet part of the base spec above.
